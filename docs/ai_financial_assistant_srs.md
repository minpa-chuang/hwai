## 引言

### 目的
本文件旨在定義 AI 理財小幫手系統之完整軟體需求，提供開發、測試、專案管理與利害關係人共同遵循的標準。文件清楚說明系統目標、功能、介面、限制與驗收準則，以確保專案交付符合預期。

本規格書涵蓋系統從資料抓取、AI 分析、報告生成到排程自動化的所有核心功能，以及可選擴充項目。文件並包含必要的非功能性需求（效能、安全、錯誤處理等）、部署與維運考量。

## 整體描述

### 產品概述
AI 理財小幫手提供個人投資者追蹤特定股票的自動化流程，包含即時股價與財經新聞收集、AI 分析摘要與情緒判斷，並輸出每日戰情報告以輔助決策。

### 系統範疇
1. 支援多支股票同時追蹤，並保留每日行情於歷史資料庫以利長期分析。
2. 每支股票對應多個新聞來源（預設 Google News 搜尋結果）。
3. 提供命令列報告（Phase 3 選項 A）與可選 Web 儀表板（Phase 3 選項 B）。
4. 產出投資組合綜覽頁面，整合各檔標的現況與專業諮詢摘要。
5. 支援排程自動化與單次臨時觸發（含單一股票分析模式）。
6. 將敏感設定（API Key、股票代碼、排程時間）外部化至設定檔或環境變數。

### 使用者特徵
- **主力使用者：** 個人投資者、投資研究員。具備基本投資知識與電腦操作能力。  
- **技術維運者：** IT/DevOps，具備部署 Python 應用與 API 管理經驗。  
- **未來可能：** 金融顧問或投資俱樂部，可能需要 Web 儀表板與多使用者存取。

### 運作環境
- **開發環境：** Python 3.9+，建議使用虛擬環境 (venv/conda)。  
- **執行環境：** Linux/MacOS/Windows 伺服器或本地機。若使用 Web 儀表板，需支援 Streamlit/Flask。  
- **排程環境：** 使用 Python schedule 函式庫或作業系統排程器（cron/Task Scheduler）。  
- **儲存：** 初版可採檔案系統儲存報告（Markdown/HTML），進階版可導入資料庫。

### 設計與實作限制
- 新聞來源需遵循 Google News 使用政策，避免過度頻繁請求。  
- OpenAI / Gemini / Perplexity 等 API 呼叫受限於配額與費用，需實作失敗重試與成本控管。
- 系統不得將 API Key 寫入程式庫檔案，需透過環境變數或安全的設定檔管理。  
- 需考量不同語系新聞來源的編碼問題（UTF-8）。  
- 排程執行需考慮台灣時間時區（UTC+8）。

### 假設與相依性
- 使用者提供合法可存取的 API Key。  
- yfinance 與 Google News 搜尋可持續提供所需資訊。  
- 網路環境穩定，請求失敗可重試。  
- 使用者具備基本 Python 執行環境。

### 成功衡量指標
- 系統可於每日指定時間產出報告，成功率 ≥ 95%。  
- 股票價量資訊準確性達 99%。  
- 新聞摘要與情緒標註準時產出，錯誤率（API 失敗導致缺漏）< 5%。  
- 報告生成流程（追蹤 2 支股票，每支 5 則新聞）在 5 分鐘內完成。

## 系統功能需求

### Phase 1：資料抓取模組

#### FR-1.1 股票資料設定讀取
- **描述：** 系統應從外部設定檔（config.py、config.json 或 .env）讀取追蹤股票代碼清單。  
- **輸入：** 設定檔。  
- **輸出：** 股票代碼列表。  
- **錯誤處理：** 設定檔不存在時記錄錯誤並停止流程。

#### FR-1.2 股價資料擷取
- **描述：** 系統應使用 yfinance 依序抓取每支股票的當日市場數據。  
- **資料欄位：** Close、Open、High、Low、Volume、Percent Change。  
- **輸出格式：** `{ticker: {price, change_percent, open, high, low, volume}}`。  
- **錯誤處理：** 若股票代碼無效或 API 失敗，應記錄警告並繼續處理其他代碼；必要時回傳空值。

#### FR-1.3 新聞資料設定讀取
- **描述：** 系統需維護股票代碼與公司中文名稱對照表於設定檔。  
- **輸出：** `{ticker: company_name}`。

#### FR-1.4 新聞清單抓取
- **描述：** 對每家公司名稱透過 Google News 搜尋取得最新新聞連結。  
- **輸入：** 公司名稱、新聞數量 N（預設 5）。  
- **輸出：** `{ticker: [{title, url}]}`。  
- **約束：** 過濾廣告/影音結果；若不足 N 則回傳可用項目並記錄警示。  
- **錯誤處理：** HTTP 錯誤或解析失敗時最多重試 3 次，仍失敗則寫入 log 並跳過。

#### FR-1.5 新聞內容擷取
- **描述：** 針對每則新聞 URL 下載文章全文並提取主要段落。  
- **輸出：** `{ticker: [{title, url, content}]}`。  
- **備註：** 可透過簡易規則或 Readability 套件清理 HTML。若網站阻擋爬蟲，須記錄狀態。

### Phase 2：AI 分析模組

#### FR-2.1 新聞摘要生成
- **描述：** 系統應根據設定使用選定的 LLM（OpenAI、Gemini 或 Perplexity）將新聞全文摘要為 3 個條列重點。
- **輸入：** 公司名稱、新聞內文。
- **輸出：** 條列式摘要字串。
- **錯誤處理：** API 失敗時重試（指數退避），超過次數後以「摘要生成失敗」占位符。

#### FR-2.2 市場情緒分析
- **描述：** 系統應透過已啟用的 LLM 根據新聞內容或摘要判斷情緒標籤（正面/負面/中性）及理由。
- **輸入：** 公司名稱、新聞摘要或全文。
- **輸出：** `{sentiment, reason}`。
- **約束：** 理由字數 ≤ 30 字。
- **錯誤處理：** 同 FR-2.1。

#### FR-2.3 多供應商策略
- **描述：** 系統需支援多個 AI 供應商的啟用/停用與主要供應商設定；當主要供應商不可用時可自動切換至備援，並紀錄各供應商諮詢結果以供投資組合綜合評估。
- **輸入：** 設定檔內的供應商參數、API Key。
- **輸出：** 各供應商回應內容及使用紀錄。

#### FR-2.4 成本控管
- **描述：** 系統須記錄每次 API 呼叫的 tokens 或費用估算，供後續成本分析。
- **輸出：** 每日成本報表（可選）。

### Phase 3：報告生成與呈現模組

#### FR-3.1 綜合點評生成
- **描述：** 系統應將股價資訊、新聞摘要與情緒分析彙整成固定 Prompt，產出約 50 字的綜合點評。  
- **輸出：** 單一字串。  
- **錯誤處理：** 同 AI 呼叫重試策略；失敗時以固定模板回報。

#### FR-3.2 報告資料結構
- **描述：** 系統需統一管理報告資料模型，包含：日期、股票基本資料、價量資訊、新聞列表（含摘要、情緒）、綜合點評。
- **格式：** Python Dict 或 dataclass；若輸出為 JSON/Markdown 需一致化欄位。

#### FR-3.3 投資組合概覽報告
- **描述：** 系統需提供投資組合層級的總覽頁面，整合各檔股票的當日行情、最新 AI 情緒、歷史走勢以及多供應商的專業諮詢摘要。
- **輸入：** 單檔報告資料、歷史股價記錄、各 LLM 供應商回覆。
- **輸出：** Markdown 或 HTML 檔案，供使用者快速掌握全局狀況。
- **內容要素：** 指標總覽表格、各檔股票近期走勢摘要、多供應商分析段落與原始報告連結。

#### FR-3.4 純文字報告輸出（Phase 3 選項 A）
- **描述：** 系統需提供可在 CLI 印出或輸出至檔案的文字報告。
- **格式要求：** 採標題、分隔線、條列式摘要與情緒。
- **檔案輸出：** 選擇性將報告存為 `reports/YYYY-MM-DD.md`。

#### FR-3.5 Web 儀表板（Phase 3 選項 B）
- **描述：** 進階版需提供 Streamlit/Flask 儀表板，顯示每日報告。
- **功能：** 股票選擇器、最新報告展示、歷史查詢、（可選）價量圖表。
- **狀態：** 選配需求，可在 Phase 3 完成後實作。

### Phase 4：自動化與擴充模組

#### FR-4.1 排程自動化
- **描述：** 系統需支援每日指定時間自動執行完整流程。  
- **實作：** 內部使用 schedule 函式庫或整合 OS 排程器。  
- **輸入：** 排程時間（預設每日 15:00 台灣時間）。  
- **監控：** 排程執行結果需寫入 log。

#### FR-4.2 通知與告警（選配）
- **描述：** 系統應提供 Email 或 Line Notify 推播報告與異常通知。  
- **觸發條件：** 排程失敗、股價觸及目標價、新聞含特定關鍵字等。

#### FR-4.3 擴充資訊來源（選配）
- **描述：** 支援社群平台（PTT、Dcard）爬取與情緒分析，作為輔助指標。
- **狀態：** 後續迭代評估。

#### FR-4.4 歷史資料管理
- **描述：** 系統應自動將每日生成的股價與情緒資訊寫入歷史檔案，支援至少一年以上的追蹤與重複執行當日更新。
- **格式：** JSON Lines 或資料庫（初版以檔案為主），需確保同一天資料可覆寫更新，並提供載入最近 N 筆資料的介面。
- **應用：** 供投資組合概覽、趨勢分析與後續擴充模組使用。

### 系統角色與權限
- **一般使用者：** 檢視每日報告、設定追蹤股票（若提供 UI）。  
- **系統管理者：** 管理 API Key、排程、通知設定、系統監控。  
- 初版若僅 CLI，可由單一使用者兼任。

## 使用案例

### UC-1：手動生成每日報告
- **主要行為者：** 系統管理者 / 使用者  
- **前置條件：** 已設定股票清單與 API Key。  
- **主要流程：**  
  1. 使用者執行主程式。  
  2. 系統抓取股價資料與新聞清單。  
  3. 系統對每則新聞進行摘要與情緒分析。  
  4. 系統生成綜合點評並輸出報告。  
  5. 系統於終端或檔案中呈現結果。  
- **例外流程：** 任一階段失敗時紀錄 log，報告顯示錯誤提示。

### UC-2：排程自動生成報告
- **主要行為者：** 排程器  
- **前置條件：** 排程已設定、系統運行中。  
- **主要流程：**  
  1. 排程器於指定時間觸發。  
  2. 系統依 UC-1 流程執行。  
  3. 報告完成後寄送或儲存至指定位置。  
- **例外流程：** 若排程觸發失敗，需發送錯誤通知或在下次排程重試。

### UC-3：設定股票與通知參數
- **主要行為者：** 系統管理者  
- **前置條件：** 系統已部署。  
- **主要流程：**  
  1. 管理者編輯設定檔或透過 UI 變更股票清單、通知關鍵字、目標價。  
  2. 系統驗證設定格式並儲存。  
  3. 後續流程使用新的設定值。  
- **例外流程：** 設定格式錯誤時回報，避免覆寫原資料。

## 資料需求
- **設定檔資料：** 股票代碼、公司名稱、新聞數量、排程時間、API Key。建議使用 JSON/YAML 或 .env。  
- **暫存資料：** 抓取的原始新聞內容、AI 回應。需有容量限制與清除策略。  
- **輸出資料：** 每日報告（Markdown/HTML/JSON），可分日期目錄儲存。  
- **日誌（Logs）：** 包含抓取結果、API 呼叫狀態、排程執行情況與錯誤資訊。

## 外部介面需求
- **使用者介面：**  
  - CLI：顯示文字報告與執行狀態。  
  - Web 儀表板（選配）：提供互動式報告瀏覽、圖表。  
- **軟體介面：**  
  - Yahoo Finance API（yfinance）：獲取股價資料。  
  - Google News（爬蟲）：取得新聞標題與連結。  
  - OpenAI API：執行摘要與情緒分析。  
  - Email/Line Notify API（選配）：推播報告。  
- **硬體介面：** 無特定硬體需求，需具備網路連線。  
- **通訊介面：** HTTPS。需支援 TLS 加密。

## 非功能性需求

### 效能
- 單次完整流程（2 支股票、每支 5 則新聞）應於 5 分鐘內完成。  
- 系統應能在 1 分鐘內回應手動生成報告的指令（不含排程等待）。

### 可用性與可靠度
- 排程執行成功率 ≥ 95%。  
- 系統應提供重試與錯誤備援機制，確保單點失敗不影響整體流程。  
- 若外部 API 當機，系統應提供降級策略（例如產出部分報告並標註缺漏）。

### 安全性
- API Key 使用環境變數或加密設定檔管理。  
- 若提供 Web 儀表板，需使用基本認證或單一密碼保護。  
- 日誌中不得直接記錄敏感憑證。

### 維護性
- 代碼應模組化，分離資料抓取、AI 分析、報告輸出與排程。  
- 提供單元測試或整合測試，至少涵蓋關鍵流程。  
- 文件需包含部署、設定與常見問題解答。

### 延展性
- 模組化設計便於加入新股票、新新聞來源、替換 LLM 或加上其他語言。  
- 報告輸出格式應可擴充為 JSON、PDF 或推播服務。

### 在地化
- 報告與提示訊息預設使用繁體中文；若需其他語系，應支援 i18n 設計。  
- 時區預設為 UTC+8，可配置。

### 合規與版權
- 遵守資料來源使用政策與爬蟲法規。  
- 需於文件中提醒使用者遵守 OpenAI、Google News 等使用條款。  
- 若報告對外發送，應加註資料來源。

## 驗收與測試規範
- **單元測試：** 針對資料抓取、摘要整合函式撰寫測試（可透過 mock）。  
- **整合測試：** 模擬完整流程（使用測試 API Key）確認報告輸出格式正確。  
- **性能測試：** 測量在不同股票/新聞數量下的執行時間。  
- **錯誤處理測試：** 模擬 API 失敗、無法解析新聞、排程異常等情境，確認系統穩定度。  
- **使用者驗收測試 (UAT)：** 與代表性使用者確認報告格式與內容符合需求。

## 部署與維運需求
- **部署腳本：** 提供 requirements.txt 或 Pipenv，說明如何安裝必要套件。  
- **環境設定：** 提供 `.env.example` 或 config 範本。  
- **監控：** 推薦整合 Logging 與簡易健康檢查。  
- **備份策略：** 報告檔案與設定檔應定期備份。  
- **更新流程:** 明定版本發布與回滾策略。
